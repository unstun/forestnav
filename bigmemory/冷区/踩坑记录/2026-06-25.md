## MinerU 本地推理链路在当前本机环境不可作为批量修复路径
- **现象**：本地 MinerU pipeline/CLI 推理路径不可用或长时间卡住；`mineru` CLI import 卡在 `pandas/numpy.random`，PDF pipeline import 卡在 `torch/torchvision` 动态库加载；marker 重转公式样本 300 秒超时且未达标。
- **原因**：会话中实际验证到当前本机 Python/native library 栈无法稳定跑通本地 MinerU/marker 批量公式修复；更底层的单一包版本或动态库根因未继续定位，不能编造成已确认结论。
- **解决**：放弃把本地推理链路作为主修复方案，改用 MinerU Open API VLM：先写 `api_trials/mineru_vlm_batch/<CitationKey>/`，通过质量门槛后再替换主库 MD 和 `_figs`。
- **预防**：未来遇到文献 PDF 公式修复，不要先在主 session 里长时间排本地 torch/marker/MinerU import；先走已验证的 API staged-replace 流程。若必须恢复本地推理，应单独开隔离任务，锁定 Python、torch/torchvision、pandas/numpy 版本并写超时/日志。

## MinerU token 不应落入本地文件或仓库
- **现象**：本机没有 MinerU token 的本地 auth 缓存；官方 CLI help 显示 `flash-extract` 无 auth、`precision extract` 需要 token，CLI 描述为 free；Dr Sun 确认 MinerU 免费。最终转换时使用临时 `MINERU_TOKEN` 环境变量。
- **原因**：会话中实际确认的是本地没有可复用 auth 缓存，而 precision/API 路径需要 token 才能调用；没有证据支持把 token 写入项目配置或用户配置文件。
- **解决**：只在命令环境中临时注入 `MINERU_TOKEN`，不写入仓库、不写入 skill、不写入持久配置。
- **预防**：后续复跑 `batch_mineru_vlm.py` 时让调用者通过 shell 环境提供 token；归档、README、skill 只能记录变量名和流程，不能记录 token 值。未来需要知道：这条边界避免把第三方 API 凭据混进文献库和 bigmemory。

## ForestNav md_dqn 基线是"假基线"（mlp-dqn 占位，非 forest 训练）
- **现象**：实验 t14 中 md_dqn 名义 algo='cnn-dqn'（`main_evaluation.py:110`、`md_dqn_adapter.py:22` 默认），但远端真实运行命令是 `--md-dqn-algo mlp-dqn`，加载 `2026-05-12..._smoke/mlp-dqn.pt`；实测 Easy SR=0.00 / Complex SR=0.02 / Extreme SR=0.01，300 个 episode 里 297 个跑满 600 步未到终点（`.pipeline/experiments/20260620_t14_candidate_6method_fullscale_md_dqn/analysis.md`）。
- **原因**：DQN10 的 `load()` 按 ckpt 内 network_kwargs 重建网络（`agents.py:912-983`），ForestNav 适配器传的裸 `AgentConfig()` / algo 字符串被 ckpt 覆盖；实际加载的是 mlp-dqn 变体（无 Double/Dueling/Munchausen/DQfD/AM），且该 ckpt 未在 forest 分布上训练过。
- **解决**：本次未修复；t14 实验已记录 md_dqn 为失败基线。
- **预防**：把 md_dqn 当基线前必须：(1) 确认 `--md-dqn-algo` 指向的变体；(2) 确认该 ckpt 在 forest 分布上训练过；否则只能视为占位，不能与 F-N3P 对比。

## L_min 训练数据与配置不一致（1.0 vs 1.5）
- **现象**：训练库 t08 用 L_min=1.0 生成（`datasets/t08_training_dataset/README.md:33`），但 `configs/default.json` 与 `2_experiment/v9_forest_n3p/design.md` 均写 L_min=1.5；`inference.py:236` 默认 `l_min_m=1.0` 与 config 同样不符。
- **原因**：历史参数（T05 时代的 1.0）未随后续设计更新同步到训练集生成脚本。
- **解决**：本次未修复；需要重训或重标时再统一。
- **预防**：重训/重标前必须先 grep 全仓库 L_min / l_min_m，确认训练脚本、配置文件、design.md 三处一致，否则训练数据与现行配置语义不一致。

## AI 文档把推算值伪造成"既有实测基线"写进 motivation
- **现象**：codex 改写的 `deep-research-report-rewrite.md` 把"F-N3P 平均多走 8%"当既有事实基线反复引用；但全仓库无任何结果文件报告 8%；实测均值≈4.3%、中位≈0.1%，只有 P95≈25% 是真实测量值（文档自身标注了"非实验数据"，但 motivation 描述未区分）。
- **原因**：deep-research 阶段工程外推数字被当成测量值落入修复方案的 motivation 叙述，AI 未主动区分"推算"与"实测"边界。
- **解决**：本次未修改报告（核验任务，非写作任务）；已在会话中标记该数字为不可信。
- **预防**：AI 产出文档里的"当前基线数字"必须回查仓库实测结果文件（如 `analysis.md`、`trial_records.csv`）后才能引用；禁止把 deep-research 推算值直接进论文 motivation 且不标注来源类型。
